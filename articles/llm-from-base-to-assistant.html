A next-token predictor can learn language without knowing how to be an assistant.

Pretraining gives us a language model. Turning that model into a useful assistant is a separate stage involving data, instruction tuning, evaluation and product constraints.

Lio Learning Path · Intermediate
Final lesson

Understand what pretraining actually teaches, why instruction tuning changes behavior, how evaluation should be designed, and what our tiny GPT can realistically demonstrate.

First, look at what we built

Across this series, text became token IDs. IDs became vectors. Vectors passed through causal self-attention and feed-forward networks. Repeated Transformer blocks produced contextual representations. A vocabulary projection produced logits. Cross-entropy turned those predictions into a loss, and optimization changed the parameters.

text → tokens → embeddings
     → Transformer → logits
     → loss → gradients → updated weights
     → decoding → generated text

That is a real language-model training pipeline, even though our model is intentionally tiny.

But what does “base model” mean?

A base causal language model is trained to continue text. If the prompt resembles a document, it may continue the document. If it sees dialogue, it may continue dialogue.

Nothing about next-token prediction guarantees that it will obey an arbitrary instruction. The model's behavior reflects the distribution it was trained on and the objective it optimized.

Instruction tuning changes the data distribution

Suppose we create examples like:

User: Explain self-attention in simple terms.
Assistant: Each token can retrieve useful information from other tokens.

We serialize the conversation, tokenize it, and train on the desired continuation. The underlying objective is still next-token prediction. What changed is the examples the model is rewarded for reproducing.

With enough diverse instruction-response examples, the model can learn patterns associated with following requests, formatting answers and maintaining conversational structure.

Why data formatting matters

Assistant training needs a consistent representation of roles and boundaries. A real system may use special control tokens or a chat template. If formatting is inconsistent, the model receives a noisy signal about where instructions end and responses begin.

<user>Explain attention</user>
<assistant>Attention routes information...</assistant>

The exact template is model-specific. The general lesson is that structure in the training examples becomes part of the learned behavior.

Preference optimization is another stage

Instruction tuning teaches the model to imitate examples. Preference-based methods introduce information about which of several candidate responses people prefer.

There are many approaches to this problem. The important conceptual separation is: architecture, pretraining, supervised post-training and preference optimization are not the same thing.

Evaluation must match the goal

A single loss number cannot tell you whether an assistant is useful. Evaluate the capabilities you actually care about.

  • Language modeling: held-out loss or perplexity.
  • Instruction following: does the response satisfy the requested format and task?
  • Factuality: does it make unsupported claims?
  • Code: does generated code run and meet the specification?
  • Robustness: does behavior remain sensible when prompts are ambiguous?
  • Safety: does the system handle disallowed or risky requests appropriately?
  • Systems: what are latency, memory and cost?

A tiny character model should not be judged as if it were a general assistant. Its success criterion is learning the narrow distribution it was trained on and giving you a working object to experiment with.

Why loss is still valuable

Loss is not useless just because it is incomplete. It gives us a clean quantitative signal for the training objective. If two models use the same tokenization and evaluation set, lower held-out cross-entropy generally means better average next-token prediction.

But a product claim such as “better assistant” needs task-specific evidence in addition to loss.

Common misconception: the model stores every sentence

Parameters encode statistical structure learned during optimization. Models can memorize some examples, especially unusual or repeated sequences, but the architecture is not a literal searchable transcript of its training corpus.

Common misconception: more parameters always wins

Scale interacts with data quality, optimization, architecture, compute and evaluation. A larger model can be more capable, but size alone does not fix a broken tokenizer, bad data or a flawed experiment.

Common misconception: attention is the whole LLM

Attention is central, but the model also depends on embeddings, positional information, MLPs, normalization, residual pathways, optimization, data and decoding.

Common misconception: good loss proves usefulness

A model can improve its likelihood objective while still failing a particular application. The correct response is not to discard the loss; it is to measure the additional behavior separately.

The final project

Now turn the series into one reproducible experiment. Train a tiny character-level GPT on a small corpus. Record the vocabulary, context length, model dimensions and parameter count.

Then change one thing at a time:

  1. Remove or alter positional information.
  2. Compare one head with multiple heads.
  3. Change context length.
  4. Plot training and validation loss.
  5. Generate the same prompt at several temperatures.
  6. Try a small instruction-style dataset and observe what changes.

Keep a lab notebook. Write down the hypothesis before each experiment and the result afterward. That turns “I built a Transformer” into actual engineering knowledge.

The mental model to keep

If someone asks what a GPT-style model does, you should now be able to trace one token through the system:

1. Tokenizer assigns an ID.
2. Embedding lookup gives it a vector.
3. Position information tells the model where it is.
4. Attention retrieves information from allowed context.
5. MLPs transform the representation.
6. Residuals carry information through the stack.
7. Final projection produces vocabulary logits.
8. Loss compares logits with the real next token.
9. Backpropagation computes gradients.
10. AdamW updates parameters.
11. Decoding turns logits into generated tokens.

Commercial systems add enormous amounts of engineering around this core: distributed training, optimized kernels, sophisticated tokenizers and data pipelines, larger architectures, post-training, evaluation and serving infrastructure. But the computational story remains recognizable.

Final checkpoint

Without looking at the previous articles, explain why token IDs need embeddings, why attention needs a causal mask, why the MLP exists, why residuals preserve shape, why training needs targets shifted by one, and why generation is different from training.

You understand an LLM when you can trace a token through the entire system—and predict what will happen when you change one part.
