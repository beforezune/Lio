LLM FROM SCRATCH · 02 · TOKENIZATION · 20 MIN READ

Before an LLM can learn language, it needs an alphabet.

A model never receives the sentence “the moon is bright” as English. It receives a sequence of integer IDs. Tokenization decides what those integers represent.

Lio Learning Path · Beginner
Learning goal

By the end, you should be able to explain vocabulary size, sequence length, subword tokens, special tokens and the one-position shift that creates next-token training examples.

The strange first step

Imagine handing a neural network the string hello. A linear layer cannot multiply a string by a matrix. The network needs numbers. The obvious first attempt is to assign every character a number:

h → 0
e → 1
l → 2
o → 3

Now hello becomes [0,1,2,2,3]. We have crossed an important boundary: language has become a sequence the computer can manipulate.

That mapping is tokenization.

Tokens are not necessarily words

A token can be a character, a whole word, part of a word, punctuation, whitespace, or a byte-level piece. Modern language models commonly use subword-style tokenization because it gives a useful compromise between vocabulary size and sequence length.

Consider the family play, playing, played. A word-level vocabulary might need separate entries for all of them. A subword vocabulary can reuse pieces:

playing → play + ing
played  → play + ed
player  → play + er

The exact splits depend on the tokenizer. The important idea is reuse: the vocabulary does not need an independent symbol for every possible word.

Vocabulary size is a trade-off

Let V be vocabulary size and T be sequence length. A larger vocabulary can represent text in fewer tokens, but the embedding table and final output projection become wider. A smaller vocabulary reduces those tables but may turn a sentence into many more positions.

This creates a real engineering trade-off. More tokens mean more Transformer positions. More vocabulary entries mean more output classes. There is no universally perfect vocabulary independent of language, data and model design.

Build the transparent version first

For our educational model, a character tokenizer is ideal because every rule is visible.

text = "hello world"
vocab = sorted(set(text))
encode = {ch: i for i, ch in enumerate(vocab)}
decode = {i: ch for ch, i in encode.items()}

ids = [encode[ch] for ch in text]
restored = "".join(decode[i] for i in ids)
print(ids)
print(restored)

The invariant matters more than the implementation: encode followed by decode should reproduce the original text exactly.

Why the token IDs have no meaning yet

If h=0 and e=1, it would be a mistake to conclude that e is somehow “one unit away” from h in meaning. The integers are labels. Their numerical ordering is arbitrary.

This becomes important later. We will use an embedding table to turn IDs into vectors. The geometry of those vectors is learned; it is not inherited from the token IDs.

Special tokens

Practical token streams often contain reserved symbols for structure: beginning-of-sequence, end-of-sequence, padding, unknown or control markers. These tokens let a model distinguish content from formatting conventions.

For our tiny causal language model, we can start without many special cases. Simplicity lets us understand the core loop before adding production concerns.

The most important shift in the whole series

Suppose our encoded stream is:

[10, 20, 30, 40, 50, 60]

For a context of four positions, we can construct:

input:  [10, 20, 30, 40]
target: [20, 30, 40, 50]

Notice the target is shifted one position to the right. At position zero, the model sees 10 and should predict 20. At position one it sees the prefix 10,20 and should predict 30.

That is next-token prediction. We do not need a separate training label for every sentence. The text itself supplies the labels.

data = torch.tensor(ids, dtype=torch.long)
x = data[i:i+block_size]
y = data[i+1:i+block_size+1]

One sequence creates many learning signals

If a context has 128 positions, a training example can provide 128 prediction targets simultaneously. With a batch of examples, the Transformer computes many of these predictions in parallel.

This is one reason language-model pretraining can consume enormous amounts of text: every sequence contains a large number of next-token decisions.

What tokenization changes

Tokenization changes the computational problem. Suppose one sentence becomes 80 character tokens but only 20 subword tokens. The same model context length now covers very different amounts of raw text.

That affects memory, attention cost and what the model can see at once. A context window of 2,000 tokens is not a fixed number of words or characters.

Common mistake: confusing token count with word count

Tokens and words are different units. Punctuation, spaces and uncommon strings can consume tokens too. This is why model context limits are normally specified in tokens rather than pages or words.

Checkpoint

Explain these four ideas without notes: a token is a discrete unit; a vocabulary maps tokens to IDs; IDs are labels rather than meanings; next-token targets are created by shifting the token stream by one position.

A useful experiment

Take a short paragraph and encode it with your character tokenizer. Count the tokens. Then imagine a subword tokenizer that groups frequent pieces. Ask what happens to sequence length and why that matters for attention.

Do not treat a tokenizer as boring preprocessing. It defines the interface between human text and the neural network.

Tokenization chooses the alphabet. Everything the Transformer learns happens after that alphabet has been written as numbers.
